## 0. 먼저, 솔직하게 알려드릴 것 3가지

1. **F12(개발자 도구)로 앱의 화면 코드가 보이는 것은 막을 수 없습니다.**
   웹/앱은 화면을 그리려면 그 코드가 폰으로 내려와야 하므로, 어떤 웹사이트든 F12로 코드가 보입니다. (네이버·인스타그램도 마찬가지입니다.)
   그래서 **"보여도 괜찮게"** 만들었습니다: 비밀번호·비밀키가 화면 코드에 **아예 없고**, 진짜 보호는 **서버(Supabase) 규칙**이 합니다.
2. **`config.js`의 주소와 공개 키(publishable/anon)는 F12로 보입니다. 정상입니다.** 이건 "집 주소"일 뿐 "열쇠"가 아닙니다.
   절대 넣으면 안 되는 것은 `service_role` / `secret` 키입니다. (이건 모든 보안 규칙을 무시하는 만능열쇠) → 넣으면 `npm run check`가 경고합니다.
3. **100% 해킹 불가능한 앱은 세상에 없습니다.** 대신 "흔하고 위험한 구멍"을 모두 막고, 막혔는지 **자동 테스트로 증명**하도록 해 두었습니다.

## 1. "남이 쓴 메시지를 다른 사람이 고치거나 지울 수 없게" — 확인 결과

**결과: 막혀 있습니다.** (제가 직접 공격을 시뮬레이션해서 확인했고, 처음부터 막히도록 만들었습니다.)

| 시도 | 결과 |
|---|---|
| B가 A의 **채팅 메시지 수정** | ❌ 거절 (0건 처리) |
| B가 A의 **채팅 메시지 삭제** | ❌ 거절 |
| B가 A의 **게시글 / 댓글 수정·삭제** | ❌ 거절 |
| B가 **A의 이름으로** 글·메시지·좋아요 작성 | ❌ 거절 |
| B가 내 글의 **작성자를 A로 바꾸기** | ❌ 거절 |
| 로그인 안 한 방문자가 글쓰기 / 채팅 읽기 | ❌ 거절 |
| 내 메시지 수정·삭제 | ✅ 가능 (정상) |
| 관리자가 규칙 위반 메시지 삭제 | ✅ 가능 (운영용) |

**어떻게 막았나요? (쉬운 비유)**
채팅 메시지 한 줄 한 줄에는 **"쓴 사람 이름표(작성자 ID)"** 가 붙어 있습니다.
누가 "이 메시지 지워줘"라고 요청하면, **서버가** 요청자의 신분(로그인 정보)과 이름표를 비교해서 **같을 때만** 허용합니다.
화면에서 버튼을 숨기는 것이 아니라 **서버 안의 규칙**이라서, 개발자 도구로 요청을 직접 보내도 소용없습니다.
이 규칙의 이름이 **RLS(Row Level Security, 줄 단위 보안)** 입니다. 파일: `supabase/migrations/003_security.sql`

## 2. 걸어 둔 규칙 전체 목록

### 🛡️ 규칙 A. 모든 데이터 보관함에 "자물쇠(RLS)" 설치
- 테이블 8개(회원, 글, 댓글, 글 좋아요, 댓글 좋아요, 채팅방, 채팅 메시지, 신고) **전부** RLS 켜짐.
- 먼저 **모든 권한을 회수(전부 잠금)** 한 뒤, 필요한 것만 하나씩 열었습니다. ("기본은 금지, 허용은 예외")
- 자동 점검이 "RLS가 꺼진 테이블이 하나도 없음"을 매번 확인합니다.

### 🛡️ 규칙 B. "칸(컬럼) 단위" 잠금 — 이중 잠금
- 회원 정보의 **권한(role)**, **차단 여부(is_banned)** 칸은 일반 회원이 **수정 권한 자체가 없음**.
  → "나를 관리자로 바꿔줘" 요청은 거절됩니다. (+ 서버 트리거가 한 번 더 막는 **2중 잠금**)
- 글의 **좋아요 수·댓글 수·숨김 여부** 칸도 직접 수정 불가. 숫자는 서버가 "+1 / -1"로만 바꿉니다. (숫자 조작 불가)
- 다른 회원의 **role, 차단 여부, 언어 설정**은 읽을 수도 없습니다. (공개 칸만 읽기 가능)

### 🛡️ 규칙 C. 관리자 페이지 잠금 (3중)
1. 일반 회원에게는 **메뉴 자체가 안 보입니다.**
2. 주소를 직접 쳐서 들어가도 **화면 안내원(라우터)이 되돌려 보냅니다.** (관리자 화면 코드는 관리자가 접근할 때만 불러옵니다. 다만 파일 자체는 공개 주소에 있어 누구나 읽을 수 있어요. 코드가 보여도 괜찮은 이유가 바로 아래 3번입니다.)
3. 설령 위 둘이 뚫려도, **서버 함수가 첫 줄에서 "당신 관리자 맞아?"를 다시 확인**하고 아니면 `forbidden` 오류를 냅니다. ← **진짜 잠금**
- 관리자 지정은 **앱에서 불가능**합니다. Supabase 대시보드의 SQL Editor에서만 가능 (README 참고).
- 관리자도 자기 자신이나 다른 관리자를 차단할 수 없습니다.

### 🛡️ 규칙 D. 비밀번호는 안전하게
- 앱 코드에 비밀번호 저장 코드가 **없습니다.** 입력된 비밀번호는 HTTPS(암호화 통신)로 Supabase Auth에 전달되고, **bcrypt로 해시(되돌릴 수 없는 형태)** 되어 저장됩니다. 운영자(저)도 원래 비밀번호를 알 수 없습니다.
- 로그인 방식은 **PKCE** (로그인 코드를 중간에 가로채도 못 쓰는 방식).
- 비밀번호 찾기에서 "가입된 이메일인지"는 일부러 알려주지 않습니다. (회원 명단 추측 방지)

### 🛡️ 규칙 E. SQL 인젝션(데이터베이스 해킹용 문장 끼워넣기) 방어
- 앱에는 **SQL 문장을 글자로 이어 붙이는 코드가 하나도 없습니다.** 모든 값은 "매개변수"로만 전달 → 입력창에 `'; DROP TABLE...` 를 써도 그냥 **글자**로 저장됩니다.
- 서버 함수에는 `search_path = ''` 를 걸어 "엉뚱한 곳의 같은 이름 테이블 바꿔치기" 공격도 차단.
- 검색어의 `, ( ) "` 같은 필터 문법 문자는 제거, `%` `_` 는 일반 글자로 처리.
- 회원 검색(관리자)도 같은 방식으로 이스케이프.

### 🛡️ 규칙 F. 화면에 글을 보여줄 때 코드 실행 차단 (XSS 방어)
- 사용자가 쓴 모든 글은 **"글자로만"** 화면에 넣습니다. (`innerHTML` 미사용)
- 실제 브라우저 테스트: 제목에 `<img onerror=...>`, 본문에 `<script>` 를 써도 **실행되지 않고 글자 그대로** 보였습니다.
- **CSP(콘텐츠 보안 정책)**: "이 앱은 내 파일과 Supabase에서 온 것만 실행/연결"하도록 브라우저에 지시. 외부 스크립트를 몰래 끼워 넣어도 실행 거부. (화면 코드는 `index.html` + `_headers`)
- 외부 CDN을 쓰지 않습니다. (Supabase 연결 라이브러리도 내 폴더 `js/vendor`에 포함)

### 🛡️ 규칙 G. 도배·악용 방지 (서버에서 강제)
| 항목 | 한도 |
|---|---|
| 글 작성 | 1시간에 10개 |
| 댓글 작성 | 10분에 20개 |
| 채팅 | 30초에 12개 |
| 신고 | 1시간에 10건 |
| 대댓글 | 1단계만 (대댓글의 대댓글 불가) |
| 길이 제한 | 제목 120 · 본문 5000 · 댓글 1000 · 채팅 500자 |

### 🛡️ 규칙 H. 사진(저장소) 보호
- 형식은 **JPG/PNG/WebP만**, 크기 **게시글 5MB / 프로필 2MB** (서버가 거절).
- 업로드·수정·삭제는 **"내 폴더"(내 회원 ID 이름의 폴더) 안에서만**. 남의 폴더 업로드 거절.
- 글에 사진 경로를 저장할 때도 서버가 **"내 폴더 경로인지"** 검사 → 남의 사진이나 외부 주소를 끼워 넣을 수 없음.
- 올리기 전에 폰에서 **사진을 다시 그려서 압축** → 촬영 위치(GPS) 등 **개인정보(EXIF)가 자동 삭제**됩니다.
- ⚠️ 사진 보관함은 **공개**입니다 (주소를 알면 누구나 열람). 여행 사진 공유용이라 의도된 설계입니다. 신분증 등 민감한 사진은 올리지 마세요.

### 🛡️ 규칙 I. 회원 가입 데이터 조작 방어
- 가입 화면에서 보낸 값은 "사용자가 마음대로 쓴 값"으로 취급하고 서버가 **전부 재검사**합니다.
  `role=admin` 을 몰래 끼워 넣어도 무시(항상 일반 회원), 이상한 닉네임/언어/국가는 안전한 기본값으로 교체.
- 닉네임은 대소문자 구분 없이 중복 불가.

### 🛡️ 규칙 J. 차단(밴) 기능
- 관리자가 회원을 차단하면 글·댓글·좋아요·채팅·신고·사진 업로드가 **서버에서** 모두 막힙니다.

### 🛡️ 규칙 K. 배포 보안 헤더
`_headers` / `vercel.json`: HTTPS 강제(HSTS), 다른 사이트가 내 앱을 액자처럼 끼워 넣는 것(클릭재킹) 차단, 불필요한 폰 기능(카메라·마이크·위치) 차단 등.

## 3. "데이터 하나 바꿀 때마다 전체가 다시 저장되나?" — 저장 로직 점검 결과

**결과: 전체 재저장 방식이 아닙니다. "바뀐 칸만" 저장합니다.** (이 앱은 새로 만든 것이라 처음부터 그렇게 설계했고, 실제 브라우저 테스트로 확인했습니다.)

| 상황 | 서버로 보내는 것 | 확인 |
|---|---|---|
| 프로필에서 **소개글만** 수정 | `{ bio }` 한 칸 | ✅ 테스트 통과 |
| 언어만 변경 | `{ language }` 한 칸 | ✅ |
| 글에서 **제목만** 수정 | `{ title }` 한 칸 | ✅ |
| 댓글 수정 | `{ body }` 한 칸 | ✅ |
| 채팅 메시지 수정 | `{ body }` 한 칸 | ✅ |
| **아무것도 안 바꾸고** 저장 | **서버 요청 자체를 안 보냄** ("바뀐 내용이 없어요" 안내) | ✅ |
| 좋아요 | 글 전체 X → **"좋아요 기록 1줄"만** 추가/삭제. 숫자는 서버가 ±1 | ✅ |
| 사진 수정 | **새로 고른 사진만** 업로드, **뺀 사진만** 삭제 | ✅ |

추가 안전장치: 저장 버튼을 두 번 눌러도 **한 번만** 저장되도록 요청 중에는 폼을 잠급니다.
핵심 코드: `js/core/utils.js`의 `diff()` 함수.

코드로는 대신할 수 없는, **대시보드에서 직접 켜야 하는** 항목입니다. (README 3단계에 클릭 순서가 있습니다.)

- [ ] **이메일 인증(Confirm email) 켜기** — 가짜 이메일 가입 방지

- [ ] **Site URL / Redirect URLs** 를 내 사이트 주소로 설정 (엉뚱한 사이트로 로그인 링크가 가는 것 방지)

- [ ] **내 Supabase 계정에 2단계 인증(2FA)** 켜기 — 계정이 뚫리면 모든 규칙이 소용없습니다
- [ ] `service_role` 키는 **어디에도 복사·저장하지 않기**

## 5-2. 지도·위치·별점 기능을 추가하며 생긴 규칙 (005)

- **별점**은 글쓴이만 줄 수 있고(내 글의 수정 권한), 1~5 의 정수만 저장됩니다. 6점·0점은 DB가 거절합니다. 남의 글 별점은 못 바꿉니다.
- **위치**: 위도/경도는 "둘 다 있거나 둘 다 없어야" 하고 올바른 범위만 허용됩니다. 장소 이름 길이도 제한됩니다. 남의 글 위치는 못 바꿉니다.
- **요약(summary)** 칸은 서버가 자동 계산하며 앱이 직접 쓸 수 없습니다.
- 위 규칙은 `supabase/tests/security_check_005.sql` (10가지 공격/정상 점검)로 실제 PostgreSQL 에서 검증했습니다.
- **개인정보 주의**: 글에 붙인 위치는 **공개**입니다(글을 보는 누구나 지도에서 볼 수 있음). 집·숙소 같은 개인 장소는 올리지 않도록 안내하세요. 사진의 촬영 위치(GPS)는 이전처럼 업로드 전에 자동으로 지워집니다.
- **내 위치 버튼**은 사용자가 직접 눌렀을 때만 브라우저가 허락을 묻고, 허락한 위치도 "핀을 꽂는 데만" 쓰이며 따로 저장되지 않습니다.
- 지도 그림·장소 검색은 외부 무료 서비스(OpenStreetMap)를 사용하므로, 지도를 열면 **사용자의 IP 주소가 OpenStreetMap 서버에 전달**됩니다(일반적인 웹 지도와 같음). 허용 외부 주소는 보안정책(CSP)에서 `tile.openstreetmap.org`, `nominatim.openstreetmap.org` 두 곳으로만 제한됩니다.
- 외부 지도 앱으로 여는 링크는 새 창 + `noopener noreferrer` 로 열립니다.
- Google 로그인의 **Client secret** 은 Supabase 대시보드에만 저장하고 앱 코드·파일에는 절대 넣지 않습니다. 앱에는 공개 가능한 값만 있습니다.

## 5-3. 프로필 항목별 공개 설정 · 이벤트 연동 (006)

- **프로필 금고 방식**: 이름·국적·거주 국가·성별·태어난 해·소개의 "진짜 값"은 본인만 읽을 수 있는 `profile_private` 표에 있고, 공개로 표시한 항목만 DB 트리거가 공개 표(`profiles`)에 복사합니다. 비공개 항목은 공개 표에서 NULL 이므로 API 를 직접 호출해도 나오지 않습니다. 공개 표의 해당 칸은 사용자가 직접 수정할 수 없고(권한 회수), 금고를 통해서만 바뀝니다. 본인은 `my_profile()` 함수로 전체를 읽습니다(익명 호출 불가). `security_check_006.sql` 26가지 점검으로 검증.
- **한국관광공사 인증키**는 Supabase Edge Function 의 Secrets(`KTO_API_KEY`)에만 있고 브라우저로 전달되지 않습니다. 행사 표(`kto_events`)는 누구나 읽기만 가능하고 쓰기는 서버 권한(service_role)만 가능합니다. Edge Function 은 JWT 검증을 끈 공개 호출 대상이므로, 6시간 캐시를 두어 남용해도 외부 API 호출이 늘지 않도록 했습니다.
- 지도 서비스 변경: `tiles.openfreemap.org`(지도 스타일·타일), `photon.komoot.io`, `nominatim.openstreetmap.org` 세 곳으로만 연결이 허용되며(CSP), 이 서비스들은 접속 시 사용자 IP 를 받습니다.

## 5-4. 모임 & 동행 · 프로필 공개 규칙 변경 (007)

- **프로필**: 이름·국적·거주 국가·성별·소개는 항상 공개, 태어난 해만 `show_age` 가 켜질 때만 공개 표에 복사됩니다(트리거 + 기존 회원 일괄 보정). 이전의 항목별 숨김 값은 무시됩니다.
- **모임**: `meetups`, `meetup_members`, `meetup_messages` 모두 RLS. 참여 신청은 본인 이름으로만 1줄 추가 가능, 상태(joined/pending)와 인원수는 트리거가 결정(정원 초과·승인제 우회·마감/취소 모임 신청 불가, 정원 동시 접수는 행 잠금). 승인/거절은 방장 전용 `meetup_decide()`. 대기 신청자 목록은 방장과 본인만 조회. **단체 채팅은 joined 상태 또는 방장만 읽기/쓰기**. 도배 방지 제한과 신고(`meetup` 유형)·관리자 숨김 연동. `security_check_007.sql` 47가지 점검으로 검증.
- **행사 사진**: 한국관광공사 서버의 사진을 브라우저가 직접 불러옵니다(CSP `img-src` 에 `*.visitkorea.or.kr` 만 추가, referrer 미전송). 이 서버는 접속 시 사용자 IP 를 받습니다.
- 한계: 사용자 간 직접 만남이므로 앱은 안전 수칙 안내·신고·숨김을 제공하지만 오프라인 만남의 안전을 보장하지 못합니다.

## 5-5. 소셜 로그인 · 회원 탈퇴 · 법적 페이지 (008)

- `delete_my_account()` 는 **본인 로그인 상태에서만** 호출 가능(비로그인 거부)하며, 계정(`auth.users`)을 삭제해 프로필·금고·글·댓글·좋아요·채팅·모임·참여 기록·소셜 연동 기록(`auth.identities`)이 연쇄 삭제되고, "나에 대한 신고"의 글 사본도 지웁니다. 사진 파일은 앱이 탈퇴 직전에 먼저 지웁니다. `security_check_008.sql` 8가지 점검.
- 카카오 연결 해제는 Edge Function `unlink-social` 이 담당합니다: 호출자의 토큰으로 **본인 확인** 후 **본인의 카카오 ID 만** 해제하고, 카카오 어드민 키는 Supabase Secrets 에만 있습니다(앱에 없음). 이 함수가 없거나 실패해도 탈퇴는 진행됩니다. 구글은 서버에서 연결을 끊는 공식 방법이 없어 이용자가 구글 계정 설정에서 직접 해제하도록 안내합니다.
- `privacy.html`, `delete-account.html` 은 스크립트·인라인 스타일이 없는 정적 페이지라 기존 CSP 를 그대로 만족합니다. 서비스워커는 이 페이지를 가로채지 않습니다.

## 5-6. 지역 칸 (009)

글/모임의 `region` 은 17개 시·도 코드 중 하나이거나 비어 있어야 하며(DB 검사), 쓰기 권한은 열 단위(`grant insert/update (region)`)로만 주어지고 남의 글/모임은 기존 RLS 가 그대로 막습니다(`security_check_009.sql` 7가지 점검). 지도에서 고른 좌표로 지역을 "추천"하는 계산은 이용자 기기에서만 일어나며 서버로 보내는 정보는 늘지 않습니다.

## 6. 솔직한 한계

- 로그인 서버(Auth)·사진 저장소(Storage)·실시간 채팅(Realtime)은 **Supabase가 제공하는 서비스**입니다. 제 작업 환경에서는 이 3가지의 **실물을 띄워서 테스트하지 못했습니다.**
  DB 규칙(RLS)은 실제 PostgreSQL로, 화면 동작은 실제 브라우저로 검증했지만, 이 3가지가 실제 Supabase와 맞물려 도는지는 **배포 후 README "7. 첫 점검 체크리스트"로 꼭 확인**해 주세요.
- 도배 방지는 계정 기준입니다. 계정을 수천 개 만드는 공격은 CAPTCHA·이메일 인증으로 막아야 합니다.
- 신고·차단은 사람이 처리하는 방식입니다. 욕설 자동 필터는 포함되어 있지 않습니다.
- 앱 사용자 수가 커지면 Supabase 요금제(무료 → Pro)를 검토하세요.
- 지도 스타일/타일(OpenFreeMap)·장소 검색(Photon/Nominatim)·한국관광공사 API·Edge Function·Google 로그인도 **실제 외부 서비스와의 연결은 제 환경에서 테스트하지 못했습니다**(브라우저 테스트는 이 서비스들을 흉내 낸 가짜 응답으로 진행). 배포 후 README 체크리스트로 확인해 주세요.

### 5-7. 게스트(익명) 채팅 보안 (010)
- 게스트 = Supabase 익명 로그인 계정. 서버 함수 `is_guest()` 가 로그인 토큰의 `is_anonymous` 를 확인합니다.
- **RESTRICTIVE 정책**(기존 허용 규칙에 "추가로 모두 통과해야 하는" 규칙)으로 게스트의 글·댓글·좋아요·모임·모임채팅·파일 업로드를 서버에서 거절. 채팅은 글자만 허용(사진/위치 칸이 있으면 거절).
- 채팅 사진 경로는 "내 폴더"만 허용(남의 사진·외부 주소 거절), 위치 좌표는 범위 검사, 사진+위치 동시 첨부 불가.
- 관심사는 5가지 목록만 허용하고 본인만 수정 가능(공개 항목).
- 점검: `supabase/tests/security_check_010.sql` (26개 항목).
